대상 DUBUFrameWork 전체 + GateWay / DUBUEchoServer 앱 코드 기준 커밋 c60431e 작성일 2026-08-18 (1번 수정 반영, 신규 N1–N5 추가) 이슈 15건(1건 수정됨) + 신규 5건 + 부록 5건 + 보류 3건
전제. 현재 EchoServer / GateWay는 디스패치 스레드가 1개라서 대부분의 이슈는 잠재 상태다. 다만 sessionCAS_(CheckSession 1스레드 제한), sessionLock_ 같은 장치는 다중 디스패치 스레드를 전제로 한 설계이므로, Server::Dispatch() / Run()을 2개 이상 스레드에서 돌리는 순간 아래 이슈들이 실제로 발화한다. 지금 1스레드 구성에서도 밟을 수 있는 항목은 1스레드도 발생으로 표시했다. RingBuffer는 알고리즘 검토 결과 프로토콜이 올바르고, 사용처가 아직 미정이라 이 문서에서 제외했다.

G 신규 확인 (2026-08-18 추가)

1번 검증 과정에서 추가 확인된 수명·프로토콜 버그. 멀티스레드와 무관하게 발생한다.

N1청크 전송 시 버퍼 1개씩 누수상 1스레드도 발생
Session.cpp:483–491 · Client.cpp:642–650 · InternalClient 동일

SendPacket이 PopPacketBuffer()로 opb를 먼저 뽑은 뒤, 크기 초과면 SendPacketChunk(...) 호출 후 return하는데 뽑아둔 opb를 반환하지 않는다. 1KB를 넘는 패킷을 보낼 때마다 OverlappedPacketBuffer 1개 영구 누수.

N2청크 크기가 정확히 나누어떨어지면 마지막 청크 유실상 1스레드도 발생
Session.cpp:644–652 · Client.cpp:798–806

size % chunckSize == 0이면 count에 +1이 없어 마지막 반복에서 sendSize = size % chunckSize = 0. 예: chunckSize 1,000에 size 2,000이면 첫 청크 1,000바이트 + 마지막 청크 0바이트 — 뒤쪽 1,000바이트가 전송되지 않고, 수신측은 chunckPacket.size_(2,000) 기준으로 조립하다 깨진 데이터를 파싱한다.

N3실패한 IOCP 완료 처리 시 버퍼 밖 65,535바이트 읽기상 1스레드도 발생
RUDPSocket.cpp:184–192 · Server.cpp:35 · Packet.cpp:5

Dispatch의 ptr == nullptr 체크는 out-파라미터의 주소라 항상 거짓이고, 호출부는 반환값 -1을 무시한 채 로컬 ptr만 본다. 취소·오류로 완료가 실패하면 ptr은 non-null, size는 -1 → Uint16으로 잘려 65,535 → PacketHeaderCheck(buffer, 65535)는 24 <= 65535라 통과 → CRC32가 1,024바이트 버퍼에서 65,535바이트를 읽는다. 크래시 가능.

N4청크 개수·크기 상한 미검증중상
Session.cpp:656 · Pool.cpp:129 · ChunkPacket.h:15

SendPacketChunk에 개수 제한이 없다. 15번째 청크(1 << 15 = 0x8000)는 DEFAULT_CHUNK_END_MASK와 겹쳐 마지막이 아닌데 END로 표시되고, 16개 초과면 Uint16 시프트가 잘려 0이 된다. 수신측 PopBig의 assert(size <= 8192) 때문에 디버그 빌드는 약 8KB부터 죽는다. 실질 상한(~8KB 디버그 / 15청크)이 어디서도 검증되지 않는다.

N5(잠재) AddSession<T>와 RemoveSession의 풀 불일치중
SessionManager.h:50 · SessionManager.cpp:35

템플릿 AddSession<T>는 Pop<T>(= ObjectPool<T>)에서 꺼내는데 RemoveSession/소멸자는 항상 Push<Session>으로 반환한다. 파생 세션(GatewaySession 정의됨)을 템플릿으로 만들기 시작하면 다른 타입 풀에 섞여 재사용 시 타입·크기가 어긋난다. 현재 템플릿 호출처 0건이라 잠재 상태.

DISCONNECT(0b11111111)는 세션이 살아 있으면 flag & REPEAT 분기로 흘러(채널 7 → g_channelMask 초과 → false) 사실상 무시되고, 세션·peer는 30초 타임아웃까지 남는다. 결정: 별도 분기를 만들지 않고 타임아웃 정리에 맡긴다. 즉시 정리가 필요해지면 세션 존재 시 DISCONNECT 분기를 추가하고, 그때 B1과 함께 처리한다.

B2 결정의 부작용. 같은 Client 객체로 Disconnect 후 재접속하면(소켓 유지 = 같은 포트 = 같은 PeerKey) 중복 SESSION 분기가 옛 세션을 그대로 돌려준다. 클라이언트 시퀀스는 0부터, 서버 recvRepeatSeq_는 옛 값이라 신뢰 패킷이 전부 del >= DEFAULT_WINDOW_COUNT로 버려지고, PING–PONG으로 timestamp_가 계속 갱신되면 타임아웃도 안 걸리는 좀비 세션이 된다. 프로세스 재시작(새 포트)은 해당 없음. 추후: 중복 SESSION 분기에서 서버측 세션 상태(rps 계열) 리셋.
